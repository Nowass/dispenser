# Dispenser v2 — Functional requirements

**Draft 0.3, 14 Nov 2026.** Scheduling decisions confirmed by Petr on 14 Nov 2026. `PROPOSED` values elsewhere remain defaults to approve. Scope: aquarium liquid-carbon dosing via ESP32-C3 with Android BLE configuration.

## Confirmed decisions

| ID | Requirement |
| --- | --- |
| FR-001 | Autonomous scheduled dosing of roughly 10–20 ml daily; exact volumetric accuracy is not critical. |
| FR-002 | ESP32-C3 normally in deep sleep, waking for planned dosing and physical button press. **M1.9b (host-tested, no deep-sleep adapter yet):** one run-to-completion cycle per wake; the plan is the earliest of next dose, next time sync and a 6 h re-evaluation cap (configurable); sleep only after the shutdown checklist. |
| FR-003 | Button on suitable deep-sleep wake GPIO activates BLE maintenance session; default 3 min advertising timeout, maintain session while connected. **M1.9b (approved policy; domain port only, no NimBLE):** a button wake opens a service session: 180 s without a client (restarted after each disconnect), kept while a client is connected, at most 15 min in total (both configurable, monotonic clock); scheduled doses suspend it and it resumes only while the deadline permits. |
| FR-004 | Android app provides schedule/configuration, calibration, manual dose, event logs, battery and estimated reservoir level. |
| FR-005 | Wi-Fi used only on important events/alerts or infrequent time sync. No routine telemetry or daily emails. **CONFIRMED (M1.7, D1-B, 2026-11-16):** Wi-Fi opens only on an existing wake: for the regular time sync (all pending notifications ride along) or, for a pending CRITICAL notification, at most once per hour and only while the Wi-Fi backoff allows it. WARNING notifications wait for the regular session. Never an extra wake-up for a notification, never during dosing, a dose permit or BLE, never close to the next dose. No delivery latency is promised. Implemented as `dsp_connectivity_run()` (host-tested). |
| FR-006 | Stock estimated in firmware; user confirms/refills volume from the Android app. No level sensor in prototype. |
| FR-007 | One low-stock alert per low-stock episode. When estimated remaining stock is insufficient for the next dose, stop automatic dosing until refill is confirmed. **CONFIRMED (M1.5, 2026-11-15):** one event per episode, then a reminder every 7 days while unresolved (see FR-021). Implemented in the firmware notification engine (M1.5, host-tested). **M1.9a (implemented, host-tested):** a persistent BLOCKED latch in the `dosing` record stops every automatic and manual dose until a completed refill; an unconfigured reservoir or pump never sets it. |
| FR-008 | Configuration persists through reboot. Device remains safe and pump off by default on startup, crashes and deep sleep. |
| FR-009 | Missed scheduled doses are **skipped, never caught up**. Multiple independent recurring schedules with different periods are supported. Before a dose, if estimated stock is insufficient for that dose, **block it** until refill confirmation. |

## Proposed functional behavior

### Schedules and doses

| ID | Requirement / default |
| --- | --- |
| FR-010 | **CONFIRMED:** independent recurring dosing events, each with its own volume, local wall-clock time, recurrence rule, start date, enable flag; support 1× weekly, multiple events daily and user-defined intervals. Maximum number of events is `PROPOSED` 8. **CONFIRMED (M1.3 brief, 2026-11-15): the device stores at most 16 schedules.** |
| FR-011 | `PROPOSED`: calibration by running pump for selected duration into a measuring vessel, then entering measured volume. Calculate ml/s, record calibration timestamp. **M1.9a:** configuration format 2 stores `pump_flow_ul_per_s` and `calibrated_at` (0 = not calibrated); no pump activation without a calibration. The calibration procedure itself needs hardware. |
| FR-012 | `PROPOSED`: use runtime-based dosing at nominal direct battery voltage. Detect/compensate voltage-dependent flow later only after physical measurements. |
| FR-013 | **CONFIRMED:** skip missed doses (do not catch up after restart or loss of time); record SKIPPED reason. **CONFIRMED (M1.2 brief, 2026-11-15):** an automatic occurrence may run only within a due window after its scheduled instant (approved: 10 minutes, tunable after RTC tests); after it, the occurrence is missed. Several accumulated occurrences are never executed after a restart. Implemented in the firmware domain (M1.2, host-tested). |
| FR-013a | **CONFIRMED:** multiple independent schedules; frequency can differ between schedules. `PROPOSED` v1 rule subset: daily every N days, weekly every N weeks with selected weekdays, monthly on day-of-month, and one-off. Optional end date. Full arbitrary iCalendar RRULE syntax is out of scope unless explicitly approved. |
| FR-013b | **CONFIRMED:** editing recurrence must not re-run old occurrences or catch up missed ones. Schedule identity and revision must be reflected in occurrence deduplication and history. |
| FR-014 | **CONFIRMED (occurrence identity, approved 2026-11-15):** each schedule occurrence has the stable ID `<scheduleId>@<localDate>` (e.g. `schedule-001@2026-11-16`), independent of the schedule revision; changing a schedule's time or volume never creates a second identity for the same local date. Schedule IDs are unique within the device and a deleted schedule's ID is never reused (mandatory invariant for the schedule-management/storage layer). **CONFIRMED (M1.3 brief, 2026-11-15):** IDs are generated by Android (UUID); the device rejects an ID that is active, among the 16 most recently deleted IDs, or present in the execution history. Beyond this bounded window, non-reuse relies on UUID uniqueness (a reused ID can only suppress, never duplicate, a dose). Multiple doses per day require multiple schedules. **CONFIRMED (M1.2 brief, 2026-11-15):** claim the occurrence durably (`STARTED`, confirmed) before the pump may start; never activate the pump if the claim fails; `STARTED` blocks like `COMPLETED`; never retry or resume a failed, interrupted or uncertain occurrence automatically (restart or power loss during dosing leaves it incomplete). Implemented in the firmware domain (M1.2, host-tested); history representation and 7-day retention approved 2026-11-15. |
| FR-015 | **CONFIRMED (A1.2b brief, 2026-11-15):** a scheduled local time that does not exist because of the spring-forward transition is skipped that day (not shifted). A local time repeated by the autumn fall-back produces exactly one occurrence, at the earlier instant, and is never administered twice. A one-off (ONCE) schedule at a nonexistent local time is rejected at entry (approved 2026-11-15). Implemented and tested in the Android recurrence engine and validator; firmware must follow the same rule. |
| FR-016 | `PROPOSED`: limits: maximum amount per individual action, maximum sum per day, maximum continuous pump runtime, cooldown between starts. Exact values TBD after pump tests. **M1.9a (approved, implemented):** configurable `max_dose_ul`, `max_daily_ul` (per Europe/Prague local date; a clock rollback never starts a new budget), `max_runtime_ms` (≤ the platform hardware cutoff) and `min_interval_s` (durable last start, survives restarts). No production defaults: 0 = not configured = no pump activation. Values are selected after pump characterization. |

### Stock and notifications

| ID | Requirement / default |
| --- | --- |
| FR-020 | Track configured reservoir volume and estimated remaining volume based on commanded completed doses; do not claim liquid flow was physically sensed. **CONFIRMED (M1.5, 2026-11-15), conservative accounting):** every authorized dose, automatic or manual, subtracts its full requested volume before the pump runs, whatever its outcome (estimate saturates at 0). A FAILED or INTERRUPTED dose marks the estimate uncertain until the next refill. Enforced by the API: the pump permit (`dsp_dose_permit_t`) exists only after a durable subtraction and is single-use; the dosing error report sets the uncertainty flag in the same write, and a refill clears it. Implemented in the firmware domain (`dsp_reservoir`, host-tested). |
| FR-021 | `PROPOSED`: low-stock at 20% remaining. **CONFIRMED (M1.5, 2026-11-15), replaces "no automatic repeated reminder"):** one notification when a low-stock episode opens, then a reminder every 7 days while it is unresolved (also for BLOCKED, low battery and persistent device errors; dosing errors are one-shot). Reminders need a trusted clock and are delivered in the next regular Wi-Fi session, never with an extra wake-up (since M1.7, D1-B: CRITICAL ones may also travel in a session on an existing wake, see FR-005). **CONFIRMED (M1.5 review):** the episode ends at threshold + 5 percentage points. |
| FR-022 | **CONFIRMED:** block the next automatic dose if estimated remaining stock is less than its requested volume. Send `EMPTY/BLOCKED` once, then sleep; do not keep retrying Wi-Fi while blocked. **CONFIRMED (M1.5, 2026-11-15):** `RESERVOIR_BLOCKED` is a CRITICAL event once per episode plus the 7-day reminder; it waits for the next regular Wi-Fi session (no extra wake-up). **Since M1.7 (D1-B):** as a CRITICAL event it may be sent during an existing wake (for example the dose wake that detected it), at most once per hour and within the Wi-Fi backoff, so "send once, then sleep" holds without retry loops. FR-022 check implemented as `dsp_reservoir_covers()`. **M1.9a:** the uncovered due dose sets the durable BLOCKED latch (before the RESERVOIR_BLOCKED report) and is not claimed. |
| FR-023 | BLE refill operation sets user-supplied new remaining amount and clears blocked state and per-episode notification latches. Validate volume and user authorization. Firmware M1.5: `dsp_reservoir_refill()` (capacity and remaining, remaining ≤ capacity) plus clearing the uncertainty flag; re-observing the estimate closes the LOW/BLOCKED episodes and withdraws their undelivered notifications. The BLE command is future work. **M1.9a:** restart-safe refill: durable intent → notification state (uncertainty cleared, BLOCKED closed) → estimate → latch cleared; dosing stays disabled until the last write, and recovery completes an interrupted refill. |
| FR-024 | `PROPOSED`: unexpected motor fault and critically low battery may cause alerts, with bounded retry policy; repeated events deduplicated. Firmware M1.5: `DOSING_ERROR` (one-shot, CRITICAL) and `BATTERY_LOW` (condition, WARNING, from a future battery monitor) are implemented in the domain; retries happen only in regular Wi-Fi sessions (approved: no extra wake-ups). |
| FR-025 | **CONFIRMED requirement, future implementation (added 2026-11-15): container replacement / tubing priming service mode.** After a container is replaced or refilled, the tubing may contain air. Workflow: (1) user starts container replacement/service; (2) normal dispensing is suspended (device state `SERVICE_REQUIRED`); (3) user confirms the tube outlet is directed into a waste container; (4) user manually controls the pump to prime the tubing; (5) pump operation has strict duration limits, an emergency stop, and fail-safe pump-OFF when communication is lost; (6) user visually confirms the tubing is filled; (7) device returns to `READY`; (8) the service operation is recorded in history. Priming volume is deducted from the reservoir estimate. History distinguishes *reservoir refilled*, *tubing primed* and *device ready for normal operation*. Not implemented in A1: no pump control, no BLE priming, no UI controls. Primary interaction: physical button, see FR-026. **M1.9a:** readiness (`READY` / `SERVICE_REQUIRED`) persisted in the `dosing` record; a new or migrated device starts `SERVICE_REQUIRED`, and `READY` requires calibration, limits and a configured reservoir. The service-mode workflow itself is future work. |
| FR-026 | **CONFIRMED requirement, future firmware (added 2026-11-15): button-driven tubing priming.** The multifunction button (FR-003) drives the service workflow of FR-025 as an explicit firmware state machine, separate from scheduled dispensing (see ARCHITECTURE "Service mode state machine"). **Gestures:** 4 short presses in READY → `SERVICE_REQUIRED` (automatic dispensing disabled). In `SERVICE_REQUIRED`, holding the button runs the pump; releasing stops it immediately. 4 short presses in `SERVICE_REQUIRED` confirm the tubing is primed → `READY`. Readiness may alternatively be confirmed via BLE. A single short press keeps its FR-003 meaning (BLE maintenance session). **Safety:** pump output fail-safe OFF (FR-044); hard maximum continuous priming runtime (pump stops even while the button is held, and restarts only after a release); a reboot never leaves `SERVICE_REQUIRED` automatically (state persisted); a button held at boot never starts the pump (the button is armed only after a release is observed); priming consumption deducted from the reservoir estimate (runtime × calibrated flow, FR-011; marked uncertain when uncalibrated); every service action recorded in history; visible feedback for each recognized gesture. **Timing:** debounce and multi-press windows defined in ARCHITECTURE; all values `PROPOSED` until hardware tests. Not implemented in A1. |

### Sleep, time, communication

| ID | Requirement / default |
| --- | --- |
| FR-030 | Timer wake for scheduled doses. GPIO wake for manual BLE maintenance. Radio remains off in deep sleep. Firmware M1.4: next-wakeup calculation (`dsp_wake_plan`) implemented and host-tested; the deep-sleep lifecycle and GPIO wake are later milestones. |
| FR-031 | Maintain UTC internal time with Europe/Prague timezone conversion for schedules/UI. Record clock-validity and last sync source/time. **Firmware M1.4 (approved 2026-11-15):** evidence-based clock trust (UNKNOWN / SYNCED / HOLDOVER without expiry); last sync, high-water time, rollback hold and last correction persisted in the `time` record (storage layout v2). |
| FR-032 | SNTP over Wi-Fi at configurable infrequent intervals; synchronize from Android time over BLE as a fallback. **CONFIRMED (M1.4 brief, 2026-11-15):** interval 24 h by default, configurable 24–48 h; Wi-Fi only during a bounded sync session; BLE is never required for regular synchronization or dosing. Implemented in the firmware domain plus ESP-IDF adapters (not yet run on a real network). The Android/BLE time fallback is still future work. Correction policy (approved): immediate step; forward steps over 10 min skip jumped-over occurrences; backward steps over 7 days hold automatic dosing until high water − 7 days. |
| FR-033 | After total power loss, do not assume clock is valid. **CONFIRMED (M1.2 brief, 2026-11-15):** clock validity must be established before automatic dosing is permitted (the M1.2 coordinator refuses automatic execution without a valid clock). Firmware M1.4: validity is recovered by an accepted SNTP synchronization (implemented, host-tested); recovery through Android/BLE is still `PROPOSED`. After a power-on reset the stored last-sync time is never used as the current time. **CONFIRMED (M1.4 review, 2026-11-15):** at every initial synchronization (previous clock untrusted) the persistent dosing floor is raised to max(floor, synchronized time + 1 s), so occurrences scheduled at or before re-establishing time are never executed (a missed dose is preferable to a possible extra one). |
| FR-034 | BLE communication with authenticated access to all mutation commands. UUIDs, versioned schema, log paging and timeout defined in separate protocol document. |
| FR-035 | Event notification: ESP sends an authenticated (bearer token; no request signing in v1) HTTPS event to a minimal endpoint that sends an email. Event IDs must be deduplicated at source and receiver. Credentials never logged. **CONFIRMED (M1.5, 2026-11-15):** at-least-once delivery. An event keeps its stable ID `dsp-<device>-<epoch>-<seq>` across retries and is removed only after an explicit acknowledgement; a failed or uncertain delivery stays queued (16-entry persistent queue, CRITICAL never evicted). Delivery happens in the next regular Wi-Fi session. A notification carries the latest known value at its first transmission attempt; its payload and freeze marker are durable before that attempt, so a retry with the same ID never changes content, also after power loss. The device ID is the factory MAC, which never serves as an authentication secret. A notification-state persistence failure is returned to the caller and logged; **it must be exposed through BLE diagnostics** in the BLE milestone. The engine and transport interface are implemented in the firmware domain (M1.5). **Backend (M1.6a, deployed):** Cloudflare Worker `dispenser-notify` + D1, protocol v1 in `cloudflare/dispenser-notify/PROTOCOL.md`; an acknowledgement means durable acceptance (`PENDING`), not e-mail delivery. **E-mail (M1.6b, deployed and verified 2026-11-16):** a 5-minute cron sends through the Gmail API from a dedicated sender account to the owner's address, Czech texts, at-least-once with stable Message-IDs (duplicates possible after an interruption); temporary failures never abandon a notification. Verified end to end in production (API ingestion → D1 → scheduled delivery → Gmail → `SENT`, no resend on the next run). **Firmware HTTPS transport (M1.7, implemented and host-tested, not yet run on hardware), approved 2026-11-16:** TLS with the full ESP-IDF certificate bundle (no pinning, verification and certificate dates always checked); HTTPS only with a trusted clock (D4; otherwise nothing is sent and the queue is kept; a CLOCK episode may therefore never produce an e-mail, R2 accepted, BLE diagnostics will expose it). ACK only after the strict confirmation body with the sent event ID (D8). Only 409 conflict and a 400 `invalid_field` naming an event-content field are permanent rejections (R1); 401, 404, 405, 413, 415, ambiguous 400s, 429 and 5xx keep the event queued and set persistent AUTH / ENDPOINT / PROTOCOL diagnostics (cleared by the next acknowledged delivery or a future BLE command), so a systemic problem can never drain the queue. A rejection is recorded in a 4-entry persistent rejection log (total and lost-unread counters) in the same atomic write that removes the entry; at most 2 rejections per session. Per-session HTTPS budget 60 s; unsent entries stay queued. Credentials (Wi-Fi, `DEVICE_API_TOKEN`) in the dedicated `nvs_sec` partition, developer-provisioned from an owner-only local file; not encrypted (physical-access risk) and one shared token for all devices (documented; per-device credentials and authenticated BLE provisioning are future work). Record formats are forward-only (R3): a future OTA must not roll back across a format change. |
| FR-036 | Failed Wi-Fi connection never blocks core dosing; short connection timeout and bounded retries. No infinite retry loops. Firmware M1.4: at most 5 attempts of at most 60 s per session (default 3 × 15 s), authentication failures not retried, exponential backoff between sessions; failures never change clock trust. |

### Logging and safety

| ID | Requirement / default |
| --- | --- |
| FR-040 | Bounded durable event log: scheduled, attempted, completed, skipped, manually requested, refilled, error, notification status. |
| FR-041 | Each record carries monotonically increasing sequence, action ID, timestamp (with validity flag), requested amount, runtime, outcome and reason. |
| FR-042 | Flash-write strategy must avoid excessive writes; no high-frequency pump-loop logging to NVS. Firmware M1.3: schedule and configuration writes only on change, two small history writes per automatic dose; estimate and wear analysis in `firmware/README.md`. |
| FR-043 | Manual dose obeys maximum run and safety limits, requires explicit action/confirmation in app, and is logged. **CONFIRMED (M1.2 brief, 2026-11-15):** a manual dose is independent of scheduled occurrence identity and never resets, clears or overwrites automatic execution history. **M1.9a:** manual doses use the same gates and limits as automatic ones, are refused while BLOCKED, require a trusted clock, and leave a durable in-flight marker with the requested volume so an interruption is reported after a restart (never re-executed). |
| FR-044 | The pump is forced OFF on all resets/failures/boot/deep sleep transitions; GPIO cannot accidentally drive it during boot. **M1.9b (host-tested):** SAFE_OFF is the first action of every wake; sleep only after the pump OFF state is confirmed; otherwise a fail-safe reset instead of sleep. Gate behavior at reset is hardware-unverified. |
| FR-045 | Test device using water only until chemical compatibility and safety are confirmed. |

## Acceptance test examples

1. Given a valid clock and an enabled schedule due now, pump starts once, runs within the configured maximum, then stops and records the event.
2. Given a reboot during dispensing, pump stays off after reboot and the same planned occurrence is not repeated automatically; event is marked interrupted/uncertain.
3. Given a due dose while stock is insufficient, pump never starts, blocking and one alert event are recorded, system sleeps.
4. Given a refill via authenticated BLE, stock updates and future scheduled doses are enabled; prior episodes remain in history.
5. Given an unavailable Wi-Fi network, alert delivery attempts are bounded and battery is not drained by retries; dosing subsystem is unaffected.
6. Given an invalid clock after power loss, scheduled pump operation remains inhibited until time is restored.
7. Given a button wake, BLE becomes available, then returns to sleep after timeout/disconnect without affecting upcoming schedules.
8. Given Android disconnect during configuration write, configuration is either fully valid/committed or remains the previous valid configuration. (Firmware M1.3: the schedule set and the configuration are each one atomic record, so the storage side of this criterion is met; host-tested, not yet on hardware.)

## Confirmed product decisions

1. **Missed dose**: skip (no catch-up).
2. **Scheduling**: multiple independent recurring calendar-style dose events, including weekly or other custom recurrence, and multiple daily events.
3. **Empty-reservoir semantics**: block before dose if estimated remaining volume cannot cover its requested amount; user must explicitly confirm refill to resume.
