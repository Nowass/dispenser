# dispenser-notify — Dispenser V2 notification backend (M1.6a)

A Cloudflare Worker that accepts notification events from Dispenser V2 devices and stores
them durably in D1. The wire format is in [`PROTOCOL.md`](PROTOCOL.md).

**Status:** implemented and tested locally. **Not deployed.** E-mail delivery is not
implemented; events are stored as `PENDING` for a later milestone.

## Architecture

```text
device (M1.5 queue)  --HTTPS POST /api/v1/events-->  Worker dispenser-notify  -->  D1 dispenser-notifications
   at-least-once,         Bearer DEVICE_API_TOKEN        validate, canonicalize,      notifications table
   stable event IDs                                      INSERT ... ON CONFLICT       (event_id PRIMARY KEY)
                                                                                       │
                                                         future milestone: e-mail sender reads PENDING rows
```

| File                                       | Purpose                                                                |
| ------------------------------------------ | ---------------------------------------------------------------------- |
| `src/index.ts`                             | routing, request limits, responses, logging                            |
| `src/auth.ts`                              | bearer-token check (constant time, fails closed)                       |
| `src/protocol.ts`                          | wire format v1 validation, canonical payload, SHA-256 hash             |
| `src/store.ts`                             | idempotent D1 insert and duplicate/conflict classification             |
| `migrations/0001_create_notifications.sql` | the deployed `notifications` schema (`IF NOT EXISTS`)                  |
| `test/ingest.test.ts`                      | Workers-runtime tests (Vitest + `@cloudflare/vitest-plugin`, local D1) |
| `test/integration/restart.mjs`             | real `wrangler dev` process, local persisted D1, restart               |
| `worker-configuration.d.ts`                | generated by `npm run types` (`wrangler types`)                        |

### Delivery boundary

1. A **201 or 200 response means the event is durably stored** in D1, and responsibility
   for delivering it passes to the backend.
2. It does **not** mean an e-mail was sent.
3. Nothing is acknowledged before the D1 insert has committed. Any storage error returns
   503, and the device keeps the event and retries with the same ID.

### Idempotency

- `event_id` is the D1 primary key. The Worker runs
  `INSERT … ON CONFLICT(event_id) DO NOTHING` and then decides:
  - row inserted → `accepted` (201);
  - otherwise it compares the stored `payload_hash`: equal → `duplicate` (200), different
    → `conflict` (409).
- Concurrent submissions of the same ID are serialized by D1, so exactly one insert wins.
- Existing rows are never updated.
- The canonical payload and hash rules are in `PROTOCOL.md`, section 2.

## Database compatibility

- `migrations/0001_create_notifications.sql` reproduces the manually created production
  schema exactly. This was verified read-only on 2026-11-15:
  - names, types, `NOT NULL`, defaults and the primary key;
  - `CHECK (delivery_status IN ('PENDING','SENT','FAILED'))`;
  - the index `idx_notifications_delivery (delivery_status, received_at)`.
- It uses `IF NOT EXISTS` throughout. Applied to production it changes no data or schema;
  it only records itself in `d1_migrations`.
- **No schema change is needed for M1.6a.**
  - The Worker writes `event_id, device_id, event_type, severity, payload, payload_hash` and
    sets `delivery_status = 'PENDING'` explicitly.
  - `received_at` and `delivery_attempts` come from their defaults.
- Compare with the real schema (read-only) before any future migration:

  ```sh
  npx wrangler d1 execute dispenser-notifications --remote --command \
    "SELECT sql FROM sqlite_master WHERE name = 'notifications'"
  ```

## Local development

Requirements: **Node.js ≥ 22.12** (wrangler 4 and Vitest 5; see `.nvmrc`). No Cloudflare
account is needed for local work.

```sh
cd cloudflare/dispenser-notify
npm ci
cp .dev.vars.example .dev.vars        # throwaway local token, ignored by git
npx wrangler d1 migrations apply dispenser-notifications --local
npm run dev                           # http://localhost:8787, local D1 under .wrangler/
```

```sh
curl -s localhost:8787/health
curl -s -X POST localhost:8787/api/v1/events \
  -H "Authorization: Bearer local-development-token-not-a-secret-0001" \
  -H "Content-Type: application/json" \
  -d '{"schema_version":1,"event_id":"dsp-0123456789ab-a5a5a5a5-1","device_id":"0123456789ab","type":"RESERVOIR_LOW","severity":"WARNING","code":null,"reminder_no":0,"created_at":1795158000,"uncertain":false,"manual":false,"value":8000,"value2":100000,"attempt":1}'
npx wrangler d1 execute dispenser-notifications --local --command "SELECT * FROM notifications"
```

## Tests and checks

| Command                    | What it does                                                                                              |
| -------------------------- | --------------------------------------------------------------------------------------------------------- |
| `npm run typecheck`        | `tsc --noEmit`, strict mode, unused-code and exact-optional checks                                        |
| `npm run format:check`     | Prettier                                                                                                  |
| `npm run lint`             | typecheck + format check (no ESLint: kept to minimal dependencies)                                        |
| `npm test`                 | Vitest inside the Workers runtime against a local D1 built from `migrations/`                             |
| `npm run test:integration` | starts `wrangler dev --local` on a temporary persisted D1, restarts it, checks durability and idempotency |
| `npm run check`            | all of the above                                                                                          |

The tests never use the Cloudflare account, the production database or a real secret.

Scenarios covered:

- health check;
- missing, invalid and valid tokens, and a missing or weak secret (fails closed);
- malformed JSON and invalid UTF-8;
- schema version, missing, unknown and invalid fields, every type and code, value ranges;
- event ID syntax, oversized bodies (declared and streamed), content type, methods;
- first submission, identical retry (different key order, number spelling and attempt),
  modified payload;
- concurrent identical and concurrent conflicting submissions;
- D1 insert and read failures, with no false acknowledgement;
- restart durability, and no read access to stored events.

## Deployment (not done yet; requires approval)

Existing resources:

| Resource | Name                                                                             |
| -------- | -------------------------------------------------------------------------------- |
| Worker   | `dispenser-notify`, `https://dispenser-notify.nowassek.workers.dev`              |
| Secret   | `DEVICE_API_TOKEN` (already set; never committed, not rotated by this milestone) |
| D1       | `dispenser-notifications`, binding `DB`                                          |

Safe deployment steps:

1. `npx wrangler login` (as the account owner) and `npx wrangler whoami`.
2. `npx wrangler d1 list`: copy the ID of `dispenser-notifications` into
   `wrangler.jsonc` (`database_id`; not a secret, so it may be committed).
3. Read-only schema comparison (command above). Stop if it differs from migration 0001.
4. `npx wrangler d1 migrations list dispenser-notifications --remote`. Then, **only with
   approval**, `npx wrangler d1 migrations apply dispenser-notifications --remote`
   (a no-op `IF NOT EXISTS`; records 0001 as applied).
5. `npx wrangler secret list`: confirm that `DEVICE_API_TOKEN` **exists**. Wrangler never
   reveals secret values, so this cannot show the secret's length or content. The deployed
   Worker validates the configuration itself (step 7).
6. `npx wrangler deploy --dry-run --outdir /tmp/dispenser-notify-dist` to review the bundle,
   then `npx wrangler deploy`.
   - This replaces the existing Worker **code**. Secrets are kept.
   - Bindings follow `wrangler.jsonc`, so check the binding diff wrangler prints.
7. Smoke test, which also verifies the secret configuration:
   - `curl https://dispenser-notify.nowassek.workers.dev/health` must answer 200.
   - `curl -i -X POST https://dispenser-notify.nowassek.workers.dev/api/v1/events` (no
     token) must answer **401**. A **503** means `DEVICE_API_TOKEN` is missing or shorter
     than 32 characters (the Worker fails closed before checking credentials, and logs
     `config_error`). Fix it with `npx wrangler secret put DEVICE_API_TOKEN`, which is a
     production secret change and needs separate approval.
   - Store nothing with a fake event in production; the integration tests cover ingestion.
8. Rollback: `npx wrangler rollback` (previous version) or the dashboard's deployments list.

## Security

- **Authentication:**
  - One shared bearer token (`DEVICE_API_TOKEN`), compared in constant time.
  - Checked before the body is read, so validation details reach only authenticated callers.
  - If the secret is missing or shorter than 32 characters, the backend fails closed (503).
- **Input:**
  - Body at most 4 KiB, enforced on `Content-Length` and while streaming.
  - Strict UTF-8 decoding and strict JSON-field validation: unknown keys are rejected,
    including `__proto__`.
  - All values range-checked; parameterized SQL only.
- **No read API:** stored events can only be read through Cloudflare (dashboard, wrangler).
- **Logging:** one JSON line per request (event, outcome, event ID, type, attempt). Never the
  `Authorization` header, the token or payload values. Event IDs contain the device MAC.
- **Errors:** minimal JSON bodies, no stack traces, `Cache-Control: no-store`.
- **Secrets:** only in Cloudflare Secrets or the ignored `.dev.vars`. `.gitignore` covers
  `.dev.vars*`, `.env*`, `.wrangler/` and `node_modules/`.

Limitations (accepted for v1, revisit before many devices exist):

- **One shared token.** Whoever holds it can submit events for any `device_id`. Per-device
  credentials (or HMAC request signing with a per-device key) bind events to devices.
- **No rate limiting or quota.** A leaked token could fill D1. Cloudflare rate-limiting
  rules or a per-device limit can be added.
- **No replay window.** Replays are harmless (idempotent), but cannot be told apart from
  genuine retries.
- **Duplicate JSON keys:** the last value wins (standard `JSON.parse`). The firmware never
  sends duplicates.
- **Token rotation:** with one shared token, rotating it requires updating every device
  first.

## Troubleshooting

| Symptom                                                         | Likely cause                                                                                                                   |
| --------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Every POST returns 503 `retry` and the log shows `config_error` | `DEVICE_API_TOKEN` not set or shorter than 32 characters                                                                       |
| 503 with `storage_error` in the log                             | D1 binding missing or misnamed (`DB`), wrong `database_id`, or a D1 outage. Devices retry automatically                        |
| 401                                                             | Token mismatch, a missing `Bearer ` prefix, or extra whitespace                                                                |
| 409 for an event                                                | The same ID was stored earlier with different content: a firmware bug or a storage-epoch collision; investigate the stored row |
| `wrangler` refuses to start                                     | Node.js older than 22.12                                                                                                       |
| `kj/async-io … disconnected` in test output                     | Expected: the Worker cancels reading an oversized streamed body                                                                |

Logs: `npx wrangler tail dispenser-notify` (production) or the console of `npm run dev`.
