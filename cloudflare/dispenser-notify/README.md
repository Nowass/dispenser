# dispenser-notify — Dispenser V2 notification backend

A Cloudflare Worker that accepts notification events from Dispenser V2 devices (M1.6a),
stores them durably in D1, and sends them by e-mail through the Gmail API (M1.6b). The
device wire format is in [`PROTOCOL.md`](PROTOCOL.md), and the Google account and OAuth
setup in [`GMAIL_SETUP.md`](GMAIL_SETUP.md).

**Status:**

- **M1.6a (ingestion):** deployed to production.
- **M1.6b (Gmail delivery):** implemented, **deployed and verified** in production
  (Worker version `271fa0d7-7008-4c3b-94b2-616c77da202c`, migrations 0001 and 0002
  applied, cron `*/5 * * * *` active). See "Production state" below.

## Architecture

```text
device (M1.5 queue) --HTTPS POST /api/v1/events--> Worker dispenser-notify --> D1 notifications
  at-least-once,        Bearer DEVICE_API_TOKEN       fetch: validate,              (PENDING)
  stable event IDs                                    canonicalize, INSERT              │
                                                                                         │
                       Cron Trigger */5 * * * * ---> Worker dispenser-notify  <──────────┘
                                                      scheduled: lease one event,
                                                      format Czech e-mail, Gmail API
                                                      users.messages.send --> recipient
```

Both roles run in the **same Worker**, sharing the `DB` binding and the secrets. Delivery
is a separate module (`src/delivery/`) with its own `scheduled` entry point. It has **no
HTTP endpoint**, and ingestion is unchanged.

### Ingestion boundary (M1.6a)

- A **201 or 200 response means the event is durably stored** in D1 as `PENDING`, and
  responsibility for delivering it passes to the backend. It does not mean an e-mail was
  sent.
- `event_id` is the primary key. The Worker runs
  `INSERT … ON CONFLICT(event_id) DO NOTHING` and then compares payload hashes: 201
  accepted, 200 duplicate, 409 conflict. Existing rows are never updated by ingestion.
- Any storage error returns 503 and is never acknowledged.

## E-mail delivery (M1.6b)

Each Cron run (every 5 minutes):

1. **Configuration:** all five delivery secrets must be present and both addresses valid.
   Otherwise the run is "disabled" (fails closed) and does nothing.
2. **Anything due?** One D1 read: `PENDING`, `next_attempt_at` reached, and not under an
   active lease. Nothing due means no Google traffic at all.
3. **Authorization wait:** while Google authorization needs attention (see Diagnostics),
   Google is contacted at most every **30 minutes**. Invalid credentials are not retried
   every 5 minutes, and events keep waiting.
4. **Token:** one access-token refresh (`grant_type=refresh_token`) **before** anything is
   claimed. A credential problem therefore never consumes delivery attempts.
5. **Up to 10 events**, each one:
   - **Lease:** an atomic `UPDATE … RETURNING` takes the next due event (CRITICAL first,
     then oldest), sets `lease_owner` (a random per-run ID) and `lease_expires_at`
     (now + 5 min), and counts the started attempt in `delivery_attempts`.
   - **Send:** format the Czech e-mail and send it through Gmail
     (`users/me/messages/send`, timeout 10 s). On HTTP 401 the token is refreshed once and
     the send retried once.
   - **Record:** every outcome is written with a fenced update
     (`WHERE lease_owner = <this run>`). It touches only delivery columns; `event_id`,
     `payload` and `payload_hash` are never written.
6. The run **stops at the first service-level failure** (temporary, rate limit,
   configuration), so retries per execution are bounded. Message-level outcomes (`FAILED`,
   an unclear 400) do **not** stop it: unrelated events are still delivered.
7. **Diagnostics:** the run updates the `delivery_state` row and logs one `delivery_health`
   line.

| Gmail / OAuth result                                                                                                        | Action                                                                                                                    |
| --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 2xx                                                                                                                         | `SENT`, `delivered_at`, `provider_message_id`; lease cleared                                                              |
| 429, 403 `rateLimitExceeded` / `userRateLimitExceeded`                                                                      | **temporary:** retry after max(backoff, `Retry-After`), no attempt limit; stop the run                                    |
| 5xx, 408, timeout, network error, any unexpected status                                                                     | **temporary:** retry after backoff, no attempt limit; stop the run                                                        |
| 413; 400 whose message names the raw payload or its size (`'raw' RFC822 payload … required`, `Invalid raw`, `too large`)    | **permanent:** `FAILED` (`gmail_413_…` / `gmail_400_invalid_payload`); health warning; continue with other events         |
| 400 that names configuration (`failedPrecondition`, `delegationDenied`, headers, sender, recipient, account, domain policy) | **configuration error:** event released, attempt **not** counted, stays `PENDING`; stop the run                           |
| 401 after a refresh, 403 (scope, account), 404, token `invalid_grant` / `invalid_client`                                    | **configuration error** (as above)                                                                                        |
| any other 400 (ambiguous, e.g. `Bad Request`, `Invalid argument`)                                                           | **unclear:** stays `PENDING` (`gmail_400_unclear_<reason>`), retried with backoff, never FAILED; health warning; continue |
| token endpoint 5xx / timeout                                                                                                | stop the run before claiming anything                                                                                     |
| stored payload unreadable                                                                                                   | **permanent:** `FAILED` (`invalid_stored_payload`); health warning; continue                                              |

Gmail's error message text is used only for this classification; it is never logged or
stored (details carry status and reason codes only).

- **Retry policy (approved):** temporary failures are retried **without an attempt
  limit**, with backoff of 1, 2, 4, 8 … minutes capped at **6 hours** (effective timing is
  rounded up to the 5-minute cron). A long Gmail outage never abandons a notification: it
  is retried about 4 times a day until it succeeds.
- **Only clearly non-recoverable errors end in `FAILED`.** HTTP 400 alone is not enough:
  it may also mean a configuration problem. A 400 becomes `FAILED` only when Gmail's
  message clearly identifies an invalid raw payload or its size; 413 and an unreadable
  stored payload are `FAILED` too. An ambiguous 400 keeps the event `PENDING` and raises a
  warning instead.
- **Configuration and authorization errors never count.** For example, a revoked token or
  the 7-day Testing-mode expiry cannot fail events. They wait as `PENDING` until an
  administrator fixes the configuration, and are delivered by the next run after that
  (within 30 minutes).

### Delivery semantics: at-least-once

- **Duplicates are possible.** Gmail can accept a message, and then the Worker can fail
  before it records `SENT`: a crash, a timeout after Gmail received the request, a lost
  lease, or a D1 error. The lease expires and the event is **sent again**. The recipient
  may then get a duplicate e-mail. This is preferred over losing a notification.
- **Message-ID:** every e-mail carries a stable `Message-ID: <event_id@dispenser-notify.invalid>`
  and `X-Dispenser-Event-Id`, so duplicates are recognizable. **Gmail is not guaranteed
  to deduplicate by Message-ID.**
- **Leases prevent concurrent duplicate sends.**
  - D1 executes the claim atomically, so overlapping Cron runs never take the same event.
  - The 5-minute lease is far longer than one send (at most about 20 s), and an expired
    lease is taken over (crash recovery).
- Reminders are separate events with their own IDs, so they produce separate e-mails.

### Diagnostics (no public endpoint)

| Question                          | Where to look                                                                                                                                                            |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| How many PENDING / FAILED         | `delivery_health` log line (`pending`, `failed`), or `npm run diagnostics:remote`                                                                                        |
| Events held by an unclear 400     | `unclear_pending`: PENDING events whose last attempt got an ambiguous Gmail 400                                                                                          |
| Age of the oldest pending event   | `oldest_pending_age_s` (seconds; `-1` = none pending)                                                                                                                    |
| Consecutive delivery failures     | `consecutive_failures`: failed runs in a row (temporary or authorization), reset by a successful send                                                                    |
| Last Gmail/OAuth error            | `last_error` (a code such as `gmail_503` or `token_invalid_grant`) and `last_error_at`                                                                                   |
| Does Gmail authorization need me? | `auth_attention = 1` (invalid or revoked credentials, missing scope or account problem, missing configuration)                                                           |
| Anything needing a look           | `level: "warn"` on `delivery_health`: authorization, **any FAILED event**, `unclear_pending > 0`, 3 or more failed runs in a row, or an event pending longer than 1 hour |

- **Logs:** every Cron run writes one structured `delivery_health` line to Workers Logs
  (observability is enabled). It goes through `console.warn` when attention is needed, so
  it can be filtered or alerted on in the Cloudflare dashboard (Workers → dispenser-notify
  → Logs, filter `level = warn` or `evt = delivery_health`). Watch live with
  `npx wrangler tail dispenser-notify`.
- **On demand:** `npm run diagnostics:remote` runs the read-only
  [`scripts/diagnostics.sql`](scripts/diagnostics.sql) through your Cloudflare login. It
  shows the health summary and the 50 oldest undelivered notifications (status,
  attempts, last error, next attempt).
- **A FAILED event keeps the warning on every run** (also after later successful runs)
  until an administrator handles it. Check `last_error`, then either requeue it (after
  fixing the cause) or delete it:

  ```sh
  npx wrangler d1 execute dispenser-notifications --remote --command \
    "UPDATE notifications SET delivery_status = 'PENDING', next_attempt_at = NULL, last_error = NULL WHERE event_id = '<id>' AND delivery_status = 'FAILED'"
  npx wrangler d1 execute dispenser-notifications --remote --command \
    "DELETE FROM notifications WHERE event_id = '<id>' AND delivery_status = 'FAILED'"
  ```

  Both are production writes: run them deliberately, one event at a time.

- None of this is reachable over HTTP. Logs contain codes and counts only, never tokens,
  addresses or e-mail content.

### Database migration 0002 (additive)

Migration 0002 adds four NULLable columns to `notifications` (`next_attempt_at` in unix
seconds, `lease_owner`, `lease_expires_at` in unix seconds, and `provider_message_id`).
It also adds one new single-row table, `delivery_state` (`consecutive_failures`,
`last_error`, `last_error_at`, `last_success_at`, `auth_attention`), for the diagnostics.

- **Why columns, not a new status:** the production `CHECK` constraint allows only
  `PENDING`, `SENT` and `FAILED`, and changing it would mean rebuilding the table. A lease
  needs no new status.
- Existing rows, the constraint, the indexes and ingestion are unchanged. Nothing is
  dropped or rebuilt.
- `ALTER TABLE … ADD COLUMN` has no `IF NOT EXISTS`. D1 migration tracking applies it
  exactly once (0001 is already recorded in production).

### E-mail example

```text
Subject: [Dávkovač V2] VAROVÁNÍ: Nízká zásoba v zásobníku (8 %)

Dávkovač V2 – upozornění

Zařízení: 01:23:45:67:89:AB
Závažnost: VAROVÁNÍ
Událost: Nízká zásoba v zásobníku

Odhadovaná zásoba klesla pod nastavenou mez. Doplňte zásobník a potvrďte doplnění v aplikaci.

Zásoba (odhad): 8 % (8,0 ml z 100,0 ml)
Odhad zásoby je nejistý: ano – po neúspěšném nebo přerušeném dávkování nemusí odpovídat skutečnosti.

Čas události: 20. 11. 2026 08:00 SEČ
Přijato serverem: 20. 11. 2026 08:12 SEČ
ID události: dsp-0123456789ab-a5a5a5a5-42

--
Automatická zpráva systému Dávkovač V2. Na tento e-mail neodpovídejte.
```

- **Format:** plain text, UTF-8, base64 body, and an RFC 2047 subject, so the whole message
  is ASCII on the wire.
- **Times** are shown in Europe/Prague (SEČ/SELČ).
- **Percentages are rounded down**, so the stock is never overstated.
- **Missing measurements are stated as missing** ("neuvedeno"; for example a battery event
  without a voltage, or a reservoir without a configured capacity), never estimated.
- **An event created while the clock was unknown** says so instead of showing a time.

## Security

- **Ingestion authentication:** one shared bearer token (`DEVICE_API_TOKEN`), compared in
  constant time and checked before the body is read. A missing or short secret fails
  closed (503).
- **Input:** body at most 4 KiB, strict UTF-8 and strict field validation (unknown keys,
  including `__proto__`, are rejected), parameterized SQL only.
- **Gmail:**
  - OAuth with the single scope `gmail.send` (the Worker cannot read mail).
  - The refresh token, client secret and both addresses are stored only as Cloudflare
    Secrets.
  - Access tokens live in memory for one run and are never logged.
  - Error details are limited to HTTP statuses and Google reason codes.
- **E-mail headers:** addresses must be plain addr-specs (no CR/LF, display names or
  comments). Header values are stripped of line breaks, and the subject is RFC 2047
  encoded.
- **No administrative or read endpoints:** delivery runs only from the Cron Trigger, and
  stored events are readable only through Cloudflare.
- **Logging:**
  - one JSON line per request or delivery attempt: event ID, outcome, attempts, error
    code;
  - never tokens, `Authorization` headers, payload values or e-mail content;
  - event IDs contain the device MAC.
- **Secrets locally:** only in the ignored `.dev.vars` or in owner-only files outside the
  repository (see `GMAIL_SETUP.md`). Revocation and rotation are in `GMAIL_SETUP.md`,
  section 6.

Limitations (accepted for now):

- **One shared device token:** whoever holds it can submit events for any `device_id`.
- **No rate limiting** on ingestion.
- **At-least-once e-mail:** duplicates are possible (see above).
- **Unverified Google app** for personal use: there is a consent-screen warning and a
  100-user cap. In Testing mode, refresh tokens expire after 7 days.
- **Permanently failed events are not re-sent automatically:** a `FAILED` event stays in
  D1 with `last_error` and keeps `delivery_health` at `warn` until an administrator
  requeues or deletes it. No second channel alerts about it.
- **Gmail 400 classification relies on Google's message text.** If Google rewords a
  message, it falls into "unclear" (PENDING plus warning), never into a wrong FAILED.
- **Gmail 400 classification untested against real rejections:** the production test
  covered the success path only.
- **Alerting needs one setup step:** the `level: "warn"` health lines are written to
  Workers Logs, but an automatic alert (for example a Cloudflare notification on log
  matches) still has to be configured in the dashboard.

## Troubleshooting

| Symptom                                                             | Likely cause                                                                                            |
| ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Every POST returns 503 `retry` and the log shows `config_error`     | `DEVICE_API_TOKEN` not set or shorter than 32 characters                                                |
| 503 with `storage_error` in the log                                 | D1 binding missing or misnamed (`DB`), wrong `database_id`, or a D1 outage; devices retry automatically |
| 401                                                                 | Token mismatch, a missing `Bearer ` prefix, or extra whitespace                                         |
| 409 for an event                                                    | The same ID was stored earlier with different content (a firmware bug or a storage-epoch collision)     |
| `delivery_config_error` in the log                                  | A Gmail secret is missing or an address is invalid; delivery is disabled                                |
| `delivery_auth_error … token_invalid_grant`                         | Refresh token revoked or expired (Testing mode: 7 days, password change, 6 months unused); re-authorize |
| `delivery_auth_error … gmail_403_insufficientPermissions`           | Token without `gmail.send`; re-authorize with the helper                                                |
| Rows stay `PENDING` with `last_error` `gmail_5xx` / `gmail_timeout` | Gmail outage; retried with backoff                                                                      |
| Row `FAILED` with `gmail_400_invalid_payload` / `gmail_413_…`       | Gmail rejected the message payload itself; investigate, then requeue or delete it (see Diagnostics)     |
| Rows `PENDING` with `gmail_400_unclear_…`                           | Ambiguous Gmail 400; check the configuration and the logs; retried with backoff, never failed           |
| Duplicate e-mail with the same `X-Dispenser-Event-Id`               | Expected at-least-once behavior after an interruption                                                   |
| `wrangler` refuses to start                                         | Node.js older than 22.12                                                                                |
| `kj/async-io … disconnected` in test output                         | Expected: the Worker cancels reading an oversized streamed body                                         |

Logs: `npx wrangler tail dispenser-notify` (production; Workers Logs are enabled) or the
console of `npm run dev`.
